# 周末聚会预算与时间计算规则

## 1. 文档用途

本文档统一 Hx-ai-life 智能体对聚会预算、AA 金额、时间轴、通勤和缓冲时间的计算口径，避免同一需求在不同对话中得到不一致的结果。

具体价格、路线耗时、营业时间和实时信息必须来自知识库或工具。本文档中的默认时长和缓冲时间是规划假设，不是第三方平台事实。

## 2. 基本原则

- 所有金额默认使用人民币“元”，除非用户明确指定其他币种；
- 区分确定价格、价格区间和未知价格；
- 区分公共费用与个人费用，不把所有费用强行平均；
- 硬预算使用保守上界校验，不能只用最低价证明“没有超预算”；
- 精确路线距离和耗时必须由地图工具返回；
- 行程时间必须包含通勤、换场和必要缓冲；
- 未核验的优惠券、满减、会员价和团购价不计入默认预算；
- 估算结果必须标注“预计”，实际消费以商家和出行平台结算为准。

## 3. 预算语义

### 3.1 硬预算

以下表达视为硬上限：

- “人均不超过 150 元”；
- “最多 600 元”；
- “一定要控制在 100 元以内”；
- “预算上限是 200 元”。

硬预算必须使用保守估算校验。保守估算超过上限时，该候选不能作为主方案，除非用户明确同意调整预算。

### 3.2 目标预算

以下表达视为软目标：

- “人均 150 元左右”；
- “大概 500 元”；
- “最好控制在 100-150 元”。

目标预算优先选择落在范围内的方案。确有明显价值时可以给出不超过目标上界 10% 的方案，但必须说明超出金额和原因，并同时提供预算内备选。

### 3.3 预算不明确

- 只有一个金额且未说明人均或总价：必须确认；
- 用户说“正常消费”“不要太贵”：可先使用 System Prompt 默认预算，但要说明默认范围；
- 用户说“预算不限”：仍需给出预计费用，不把“无限预算”理解为可以忽略性价比；
- 人数未知且涉及总价或 AA：先确认人数。

## 4. 费用范围

### 4.1 公共费用

默认需要多人共同承担的费用：

- 餐饮；
- 活动门票、包间或场地费；
- 共同乘坐的出租车或网约车；
- 用户明确要求共同购买的其他项目。

### 4.2 个人费用

默认由个人承担、不直接均分的费用：

- 各成员从不同出发地到集合点的交通；
- 个人加购、酒水或额外服务；
- 停车费等仅由部分成员产生的费用；
- 未参与某项活动的成员对应费用。

### 4.3 默认预算口径

用户只说“人均预算”时，默认指餐饮、活动和共同交通的人均费用。成员从不同地点出发产生的个人往返交通应单独列出，不计入统一 AA 总额。

如果个人交通可能决定方案是否超预算，应明确列出“公共人均”和“含个人交通的预计人均”；不能确定所有人的交通费时，不给出虚假的统一总额。

## 5. 金额取值规则

### 5.1 单一价格

知识库或工具返回单一价格时，直接作为该项预计值，并保留来源和核验日期。

### 5.2 价格区间

价格为 `[最低价, 最高价]` 时：

- 期望估算 = `(最低价 + 最高价) / 2`；
- 保守估算 = `最高价`；
- 硬预算校验使用保守估算；
- 向用户展示区间，不只展示中间值。

### 5.3 未知价格

- 关键项目价格未知时，不计算精确总价；
- 可以汇总已知部分，并写“另加价格待确认的项目”；
- 硬预算场景下，价格未知的候选不能被描述为确定满足预算；
- 不用同类型店铺的平均价格冒充该店价格。

### 5.4 优惠与押金

- 只有本次工具调用或已核验数据确认可用的优惠，才可列为“可用优惠”；
- 需要满足条件的优惠必须同时说明门槛；
- 未确认领取或购买成功前，原价用于硬预算校验；
- 可抵扣消费的订金只计算一次；
- 可退押金不计入最终消费，但应列入出发前需要准备的资金。

### 5.5 税费和服务费

已知存在服务费、包间费、最低消费或平台手续费时，应单独计入。是否存在无法确认时，不得写成“无服务费”，应提醒用户向商家确认。

## 6. 预算计算公式

设：

- `N` = 参与总人数；
- `N_i` = 参与第 `i` 项活动的人数；
- `F_food` = 餐饮总费用；
- `F_activity_i` = 第 `i` 项活动总费用；
- `F_shared_transport` = 共同交通总费用；
- `F_other` = 其他共同费用。

公共总费用：

```text
公共总费用 = F_food + ΣF_activity_i + F_shared_transport + F_other
```

所有人参与相同项目时：

```text
公共人均 = 公共总费用 / N
```

参与人数不同或存在个人加购时，按项目分别计算：

```text
个人应付 = 餐饮分摊 + Σ(本人参与项目总价 / 该项目参与人数) + 本人个人费用
```

不得让未参与某项活动的人承担该项费用，除非用户明确决定平均分摊。

### 6.1 舍入规则

- 对用户展示的单项人均保留到 1 元；
- AA 转账建议金额向上取整到 1 元，避免公共支付人垫付不足；
- 分项四舍五入可能造成总和误差时，以公共总费用为准，并将尾差计入公共支付人的应收金额；
- 不通过隐藏小数或遗漏费用让方案看起来刚好满足预算。

## 7. 预算校验与调整

### 7.1 双口径校验

每个方案同时计算：

- `期望人均`：使用价格区间中值，用于展示通常消费水平；
- `保守人均`：使用价格上界和已知必要费用，用于检查硬预算。

输出示例：`预计人均 138-162 元；按保守口径可能超过 150 元上限，因此不作为主方案。`

### 7.2 超预算时的调整顺序

在不破坏用户硬约束的前提下，依次尝试：

1. 替换同类型、同商圈但价格更低的餐厅；
2. 替换活动档位、时长或场次；
3. 减少非核心付费项目；
4. 优化共同交通方式；
5. 更换相邻商圈。

不得通过假设存在优惠、少算返程、漏掉服务费或使用价格下界来掩盖超预算。

如果所有候选都无法满足硬预算，应说明最低可行预算，并询问用户优先调整预算、地点还是活动。

## 8. 时间信息分类

### 8.1 固定时间

不可随意移动的时间：

- 电影、演出、展览预约场次；
- 餐厅预约时间；
- 用户明确的集合、到达或离开时间；
- 公共交通末班时间等已由工具确认的限制。

固定时间是时间轴锚点，应先放入时间轴，再向前或向后安排其他项目。

### 8.2 工具时间

地图、票务、天气或其他工具返回的时间，包括路线耗时、场次时长和营业时间。必须保留查询条件和更新时间，不得用模型常识修改。

### 8.3 规划假设

知识库没有明确时长时，可使用本文档的默认时长。输出中无需逐项强调“模型假设”，但应统一标为“建议安排”或“预留”，不能伪装成商家规定。

## 9. 默认活动时长

以下时长仅用于初步规划，可被用户需求或可靠数据覆盖：

| 项目 | 默认时长 |
| --- | ---: |
| 简餐、咖啡 | 60 分钟 |
| 普通正餐 | 90 分钟 |
| 火锅、烤肉、自助餐 | 120 分钟 |
| 电影 | 影片实际时长 + 30 分钟入场和散场 |
| 桌游 | 120 分钟 |
| KTV | 120 分钟 |
| 密室、剧本类活动 | 使用商家场次时长；未知时先确认 |
| 展览、博物馆 | 90 分钟 |
| 商圈散步、夜景 | 45-60 分钟 |
| 咖啡或甜品续场 | 60 分钟 |

用户明确说“想慢慢聊”“只简单吃点”等情况，应相应调整，不机械套用默认值。

## 10. 通勤和换场时间

### 10.1 路线时间

- 精确路线耗时、距离、换乘和费用来自 `plan_route`；
- 用户指定未来出发时间时，优先使用支持指定时间的路线结果；
- 只有当前实时路况时，不将其当作未来时段的确定耗时；
- 多人从不同地点出发时，分别计算主要成员路线。

### 10.2 执行缓冲

地图工具返回的 ETA 之外，按场景增加规划缓冲：

| 场景 | 建议缓冲 |
| --- | ---: |
| 同一商场或相邻楼层换场 | 10 分钟 |
| 商圈内步行换场 | 路线耗时 + 10 分钟 |
| 地铁或公交到店 | 路线耗时 + 10-15 分钟 |
| 打车到店 | 路线耗时 + 10 分钟上下车和寻车时间 |
| 预约餐厅或固定场次签到 | 额外提前 10-15 分钟到达 |
| 节假日、恶劣天气或大型活动周边 | 在正常缓冲上再增加 10-20 分钟 |

缓冲时间用于提高方案可执行性，不等于平台预测的路线延误。

### 10.3 排队预留

没有实时排队数据时，不生成“预计等待 X 分钟”的实时结论。为安排时间轴，可以按历史热度设置计划预留：

| 历史热度 | 建议计划预留 |
| --- | ---: |
| 低 | 10 分钟 |
| 中 | 20-30 分钟 |
| 高 | 45-60 分钟，优先预约或错峰 |
| 未知 | 20 分钟，并要求出发前确认 |

必须将其称为“计划预留”，不能称为“当前等待时间”。已预约并确认无需候位时，可以缩短预留，但仍保留签到时间。

## 11. 时间轴生成顺序

按以下顺序生成行程：

1. 放置电影、演出、预约等固定时间；
2. 根据活动和用餐顺序放置核心项目；
3. 使用地图工具计算出发和换场时间；
4. 加入签到、寻路和排队预留；
5. 检查营业时间、最晚入场和返程限制；
6. 检查是否存在时间重叠或过紧衔接；
7. 给出建议集合时间和最晚出发时间。

若没有固定时间，默认优先保证用餐时段合理，再安排相邻活动，避免为了塞入更多项目导致频繁换场。

## 12. 营业时间校验

- 计划开始时间必须晚于开门时间；
- 计划结束时间应早于关门时间；
- 已知最晚点餐、最晚入场或停止检票时间时，以这些时间为准；
- 只知道关门时间时，建议最晚开始时间 = 关门时间 - 项目时长 - 30 分钟余量；
- 营业时间已过有效期或可能受节假日影响时，应提示用户再次确认；
- 无法确认营业时间的候选不能作为高确定性的主方案。

## 13. 多人出发时间

多人从不同地点出发时：

1. 为每个主要出发地获取路线耗时；
2. 以共同集合时间倒推出各自最晚出发时间；
3. 比较最长通勤和平均通勤，避免只按几何中点选商圈；
4. 有成员必须提前离开时，检查其返程路线和离开节点；
5. 不把不同成员的个人交通费平均计入公共 AA。

建议展示：`A 最晚 17:35 出发，B 最晚 17:50 出发，18:30 在餐厅集合。`

## 14. 时间冲突处理

时间轴无法成立时，依次尝试：

1. 缩短非核心自由活动；
2. 选择更近的同类型活动或餐厅；
3. 调整非固定项目顺序；
4. 更换可用场次；
5. 删除优先级最低的项目。

不得压缩地图工具返回的通勤时间，也不得忽略签到、散场或必要换场缓冲来制造“刚好赶上”的假象。

## 15. 计算示例

用户需求：4 人，餐饮加活动人均不超过 150 元，成员从不同地点自行前往集合点。

候选方案数据：

- 餐厅人均 90-110 元；
- 活动票 35 元/人；
- 饭后共同打车预计 28-36 元；
- 个人前往集合点的费用不同，单独计算。

计算：

```text
期望餐饮总价 = (90 + 110) / 2 × 4 = 400 元
保守餐饮总价 = 110 × 4 = 440 元
活动总价 = 35 × 4 = 140 元
共同打车期望价 = (28 + 36) / 2 = 32 元
共同打车保守价 = 36 元

期望公共总价 = 400 + 140 + 32 = 572 元
期望公共人均 = 572 / 4 = 143 元

保守公共总价 = 440 + 140 + 36 = 616 元
保守公共人均 = 616 / 4 = 154 元
```

结论：期望人均在 150 元内，但保守人均为 154 元，不能确定满足硬预算。应替换更低价餐厅或活动，不能仅按期望值将其作为主方案。

## 16. 标准输出格式

```text
预算：
- 餐饮：预计 XX-XX 元/人
- 活动：预计 XX 元/人
- 共同交通：预计 XX-XX 元，共同乘坐者约 XX-XX 元/人
- 公共费用合计：预计 XX-XX 元
- 公共人均：预计 XX-XX 元
- 个人往返交通：按各自出发地另计

时间轴：
- HH:mm 集合
- HH:mm-HH:mm 用餐
- HH:mm-HH:mm 换场（含 XX 分钟缓冲）
- HH:mm-HH:mm 活动

说明：价格和时间为规划估算；实时营业、排队和出行费用以对应平台实际信息为准。
```

## 17. 输出前检查清单

- [ ] 已判断预算是人均还是总价、硬上限还是软目标；
- [ ] 已区分公共费用和个人费用；
- [ ] 价格区间同时计算了期望值和保守值；
- [ ] 未使用未经核验的优惠降低预算；
- [ ] 硬预算按保守人均校验；
- [ ] 精确路线耗时来自地图工具；
- [ ] 时间轴包含换场、签到和必要缓冲；
- [ ] 排队预留没有写成实时等待时间；
- [ ] 已检查营业时间、固定场次和返程限制；
- [ ] AA 没有向未参与者分摊项目费用；
- [ ] 估算项和未知项已明确标注。

## 18. 维护规则

- 默认时长和缓冲应根据真实用户反馈调整，不因单个案例频繁变化；
- 具体店铺价格和营业时间不得写入本文档；
- 地图平台的接口字段、计费和时效规则由平台边界文档维护；
- 计算规则变化后，至少复算本文档示例和一组边界案例；
- 每次修改更新 `version` 和 `last_verified_at`。
