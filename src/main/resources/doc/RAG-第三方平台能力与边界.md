# 第三方平台能力与边界知识库

## 1. 文档用途

本文档供 Hx-ai-life 智能体在推荐餐厅、规划活动、计算通勤、说明排队情况和生成 PDF 时检索使用。

本文档解决以下问题：

- 哪些信息可以直接展示，哪些信息必须调用工具获取；
- 哪些第三方平台能力可以作为入口，哪些能力不能对用户承诺；
- 数据缺失、过期、冲突或工具失败时如何处理；
- 如何避免编造实时信息、虚假链接和未经证实的平台能力。

本文档不是美团、大众点评、小红书、高德或百度等平台的官方规则，也不替代其最新开发者协议。涉及接口、链接、授权和商用范围时，以对应平台最新官方文档及实际测试结果为准。

## 2. 核心原则

### 2.1 信息来源原则

信息按可信度从高到低排序：

1. 本次工具调用返回的官方或授权数据；
2. 已人工核验且仍在有效期内的精选知识库数据；
3. 地图 POI 等公开检索结果；
4. 用户在当前对话中提供的信息；
5. 历史经验、商圈规律或其他非实时参考信息。

低优先级来源不得覆盖高优先级来源。来源相同但内容冲突时，优先采用更新时间较新的信息；无法判断时，应向用户说明存在差异，不自行选择一个结果冒充确定事实。

### 2.2 动态数据原则

下列信息属于动态数据：

- 实时排队桌数和预计等待时间；
- 营业状态、临时闭店和临时调整后的营业时间；
- 实时路况、路线耗时和公共交通到站时间；
- 即时价格、优惠、团购套餐和活动票价；
- 评分、评论数量、活动排期和余票；
- 预订、取号或预约是否成功。

动态数据必须来自本次有效工具调用或用户打开的第三方平台页面。知识库中的历史记录只能作为参考，不得表述为当前实时状态。

### 2.3 不编造原则

不得编造以下内容：

- 店铺评分、人均价格、营业时间、地址和评价；
- 实时排队桌数、等待分钟数或取号结果；
- 路线距离、耗时、费用和拥堵状态；
- 第三方平台的店铺链接、取号链接、小程序路径或 App Scheme；
- API 已开放、接口可商用、平台已授权等结论；
- 用户已经完成预订、购票、取号或支付。

信息不足时应明确标记“暂无可靠数据”或“需在第三方平台确认”。

## 3. 平台能力说明

### 3.1 美团与大众点评

#### 可用于产品的能力

- 展示知识库中已经人工核验的店铺页或分享链接；
- 引导用户进入对应店铺页面查看实时营业、优惠、预订和排队入口；
- 使用人工整理并标注日期的价格、评分、营业时间和历史排队规律；
- 在获得正式开放接口和所需授权后，调用接口返回其许可范围内的数据。

#### 不应默认承诺的能力

- 不承诺每家店都提供线上排队或取号；
- 不承诺店铺页链接可以直接进入排队页面；
- 不承诺网页链接一定能唤起 App；
- 不承诺存在长期稳定的通用深度链接、App Scheme 或小程序路径；
- 未获得官方接口授权时，不承诺自动读取实时排队、团购、预订或评价数据；
- 不通过模拟登录、绕过风控或批量抓取来获取平台内受限数据。

#### 推荐输出规则

- 知识库有已核验店铺链接：展示“查看店铺详情”入口；只有已确认该入口支持排队时，才可标为“查看排队/取号”。
- 只有店铺页、不确定是否支持排队：写“可进入店铺页查看是否支持在线排队”。
- 没有已核验链接：不拼接链接，写“暂无已核验的平台入口，可在美团或大众点评搜索店名”。
- 排队信息不是实时工具返回：必须注明“这是历史时段热度，不代表当前排队情况”。

### 3.2 小红书

#### 可用于产品的能力

- 向用户提供平台内搜索建议，例如“城市 + 店名 + 排队”或“城市 + 店名 + 避雷”；
- 展示已经人工核验、允许分享的公开页面或搜索入口；
- 将公开内容作为人工维护餐厅档案时的参考来源，并记录核验日期。

#### 不应默认承诺的能力

- 不承诺搜索结果完整、最新或客观；
- 不把单篇笔记的个人体验当作普遍事实；
- 不自动批量抓取登录后内容、评论、作者信息或受限数据；
- 不从用户笔记推断或保存与行程规划无关的个人敏感信息；
- 不自行构造未经验证的 App Scheme 或小程序直达路径。

#### 推荐输出规则

- 小红书内容只作为用户口碑和现场体验参考，不作为实时营业、价格或排队数据的唯一依据。
- 多个来源结论不一致时，写“用户体验存在差异”，并建议结合店铺官方页面确认。
- 引用人工提炼结论时，应同时保留来源类型、核验日期和样本量；样本不足时标记“低置信度”。

### 3.3 高德、百度等地图平台

#### 可用于产品的能力

在已申请有效 API Key、接口权限满足要求且调用成功时，可以使用地图工具完成：

- 地址解析与坐标转换；
- 餐厅、活动场所和周边 POI 检索；
- 驾车、公共交通、步行和骑行路线规划；
- 返回路线距离、预计耗时、换乘信息和接口明确提供的费用；
- 使用接口明确提供的实时路况或预测路线信息。

具体字段、配额、计费、可用城市及商用条件以平台最新官方文档和开发者账号权限为准。

#### 路线推荐规则

- 有明确出发地、目的地和出发时间时，调用 `plan_route`，不得凭经验生成精确距离和耗时。
- 用户计划未来出发时，不把当前路况描述为出发时路况；若工具提供指定时间预测，应标记为“预测”。
- 路线结果缺少某种交通方式时，只比较工具实际返回的方案。
- 聚会可能饮酒时，提示不要酒后驾车，并优先比较公共交通和打车方案。
- 步行距离、天气、换乘次数和同行人数可用于解释推荐，但不得修改工具返回的事实数据。
- 费用为估算值时明确写“预计”，实际金额以出行平台结算为准。

#### 工具失败时的降级

- 地图工具失败：不输出精确通勤时长，改为说明“路线服务暂不可用”。
- POI 检索无结果：请用户补充城市、区县、商圈或完整地址。
- 同名地点无法消歧：列出候选地点并让用户确认，不自行选择。
- 坐标或行政区明显冲突：停止路线计算，先确认地点。

### 3.4 天气服务

如产品接入天气工具，可用天气结果辅助选择室内或户外活动。天气预报必须包含目标城市、日期、数据来源和更新时间。

- 不用模型常识生成具体温度、降雨概率或预警；
- 预报日期超出工具支持范围时，明确说明无法可靠预测；
- 极端天气或官方预警下，优先建议室内或延期，并提示以当地官方预警为准；
- 天气工具失败时，不假装天气正常，只说明暂未取得天气数据。

## 4. 排队与人流规则

### 4.1 信息分类

排队与人流信息分为三类：

| 类型 | 示例 | 可否作为当前事实 |
| --- | --- | --- |
| 实时排队 | 当前前方 12 桌、预计等待 35 分钟 | 仅本次官方或授权工具返回时可以 |
| 预测热度 | 预计周六 19:00 为高峰 | 可以，但必须标为预测 |
| 历史规律 | 近期香港用户反馈周末晚餐较拥挤 | 可以作为参考，不可表述为实时 |

### 4.2 历史热度等级

知识库统一使用以下等级，避免用缺乏依据的精确分钟数：

- `低`：通常无需专门错峰，但仍需以现场为准；
- `中`：可能需要短时等候，建议提前查看或预约；
- `高`：高峰时段可能明显等候，建议预约、提前到店或选择备选；
- `未知`：没有足够且近期的数据。

如果历史资料中存在等待时间范围，可保留原始描述及来源日期，但输出时必须写成历史参考，例如：“根据 2026-07 的人工核验记录，周六晚曾出现约 30-60 分钟等候；当前情况请在平台确认。”

### 4.3 标准话术

- 有历史热度、无实时数据：`该时段历史热度为高，仅供错峰参考；实时排队请在店铺页面或到店前确认。`
- 没有排队数据：`暂无可靠排队数据，建议出发前在美团/大众点评店铺页确认是否支持在线排队。`
- 店铺不支持线上取号：`目前没有已核验的线上取号入口，建议电话咨询或到店确认。`
- 工具返回实时结果：`截至 {更新时间}，平台显示 {结果}；排队变化较快，以提交取号时的页面为准。`

## 5. 店铺与活动数据时效

### 5.1 建议有效期

| 数据字段 | 建议有效期 | 过期后的处理 |
| --- | --- | --- |
| 地址、店名、平台链接 | 90 天 | 可展示，但标记待复核；跳转失败则停用 |
| 营业时间、联系电话 | 30 天 | 不作为确定事实，提示平台确认 |
| 人均价格、票价 | 30 天 | 仅作预算估算，标明核验日期 |
| 评分、评论数 | 14 天 | 标明来源和日期，禁止称为实时评分 |
| 历史排队规律 | 30 天 | 降低置信度，节假日前重新核验 |
| 活动排期、展览、演出 | 7 天或截至结束日 | 超过结束日立即停用 |
| 实时路况、实时排队 | 仅本次调用 | 不写回为长期事实 |

有效期是产品内部建议，不代表第三方平台保证。运营人员可根据实际更新成本调整，但必须统一记录变更。

### 5.2 每条数据应保存的元数据

```yaml
source_type: official_api | verified_platform_page | manual_research | user_provided
source_platform: amap | baidu_map | meituan | dianping | xiaohongshu | merchant | other
source_url: 已核验的原始链接，没有则留空
verified_at: 2026-08-21T10:00:00+08:00
expires_at: 2026-09-20T10:00:00+08:00
confidence: high | medium | low
verified_by: 人员或任务编号
notes: 核验方式及限制
```

## 6. 链接与二维码规则

- 链接只能来自官方/授权工具返回、商家公开入口或人工核验后的知识库字段。
- 不根据店铺 ID 猜测 URL，不自行拼接平台深度链接。
- 生成 PDF 前应检查链接协议、域名和基本可访问性；需要登录才能看到内容不等于链接无效，但应注明“可能需要登录或打开 App”。
- 二维码应编码已核验的 HTTPS 页面地址；除非已经完成目标设备验证，否则不使用私有 Scheme。
- 展示文案必须与落地页一致：店铺页写“查看店铺”，只有排队页才写“立即取号”。
- 链接失效、跳错店、域名异常或平台归属不明时，停止展示该入口并进入人工复核。

## 7. 推荐与商业公平

- 推荐理由必须对应用户明确需求，例如预算、口味、忌口、距离、人数、日期和活动偏好。
- 商业合作、广告、佣金链接或赞助排序必须清晰标记，不得伪装成客观最佳推荐。
- 缺少评分或热度数据不等于店铺质量差，只能写“暂无数据”。
- 不根据姓名、性别、民族、职业、收入等敏感或无关特征实施歧视性推荐。
- 用户有过敏、宗教饮食或医疗相关忌口时，应优先筛除不兼容选项，并提醒向商家再次确认配料和交叉污染风险。

## 8. 用户信息与隐私边界

### 8.1 可以收集的信息

仅在完成规划所必需时收集：

- 城市、商圈或大致出发位置；
- 日期、时段、人数和预算；
- 菜系、活动偏好、忌口和无障碍需求；
- 用户主动选择保存的常驻城市、预算习惯和常用商圈。

### 8.2 不应收集或输出的信息

- 第三方平台账号密码、短信验证码、支付密码；
- 身份证号、银行卡号等与规划无关的敏感信息；
- 未经同意的精确长期位置轨迹；
- 其他同行人的联系方式、身份信息或隐私偏好；
- 第三方平台登录 Cookie、Token 或其他会话凭证。

用户误发敏感信息时，不在回复中复述完整内容，并提示用户删除或撤回；日志和存储应按系统安全策略脱敏。

## 9. 异常与降级策略

| 场景 | 处理方式 | 禁止行为 |
| --- | --- | --- |
| 餐厅知识库无结果 | 使用地图 POI 补充，并标注“非精选数据” | 编造评分、价格或排队规律 |
| 店铺信息过期 | 提供参考值和核验日期，提示再次确认 | 把旧数据称为当前数据 |
| 店铺链接缺失 | 建议用户按“城市 + 店名”搜索 | 猜测或拼接链接 |
| 实时排队不可用 | 提供历史热度和平台确认入口 | 生成具体桌数或等待时间 |
| 路线工具失败 | 保留地点方案，说明暂不能给出精确路线 | 凭印象填写精确耗时 |
| 多来源信息冲突 | 展示差异，优先最新高可信来源 | 静默挑选有利结果 |
| PDF 生成失败 | 返回完整文字方案和有效链接 | 只回复“生成失败” |
| 用户要求代登录/绕过限制 | 拒绝获取凭证或规避风控，提供官方入口 | 保存凭证、模拟违规访问 |

## 10. Agent 决策流程

```text
收到规划需求
  -> 判断是否缺少城市、日期、人数、预算等关键约束
  -> 检索精选餐厅/活动知识库
  -> 检查数据来源、核验日期、有效期和置信度
  -> 必要时调用地图、天气或其他授权工具
  -> 区分实时事实、预测结果和历史参考
  -> 按匹配度、预算、通勤、人流和口碑生成主方案与一个备选
  -> 为动态信息增加更新时间或确认提示
  -> 仅展示已核验的第三方入口
  -> 用户确认后生成 PDF
```

## 11. 输出前检查清单

生成聊天方案或 PDF 前检查：

- [ ] 店名、地址和城市没有混淆；
- [ ] 评分、人均、营业时间均有来源和核验日期；
- [ ] 实时信息来自本次工具调用，并标明更新时间；
- [ ] 预测和历史规律没有写成实时事实；
- [ ] 精确路线数据来自地图工具；
- [ ] 所有链接均来自已核验字段，没有自行拼接；
- [ ] 链接按钮文案与实际落地页能力一致；
- [ ] 预算中的估算项已明确标注；
- [ ] 方案包含一个主推荐和一个差异明确的备选；
- [ ] 涉及饮酒、过敏、极端天气等风险时已给出必要提醒；
- [ ] 未输出用户或同行人的敏感信息。

## 12. 知识库维护规则

- 每次修改本文档时更新 `version` 和 `last_verified_at`；
- 平台链接规则、API 能力、配额、授权和商用条件至少每 30 天复核一次；
- 只将已实际验证的平台能力写成“可用”，计划中或听说的能力写成“待验证”；
- 发现链接失效或能力变化时，立即标记停用，不等待下一个复核周期；
- 保留变更记录，记录修改日期、修改人、事实来源和影响范围；
- 平台官方规则与本文档冲突时，以最新官方规则为准，并更新本文档。
